04 / 07

Lookup on
the Ring.

# Consistent hashing lookup def get_server(key, ring): h = hash(key) # first node clockwise from h for node_hash in sorted(ring.keys()): if node_hash >= h: return ring[node_hash] return ring[min(ring.keys())] # wrap around

Removing N2 only affects the keys that were pointing at N2. Everyone else on the ring keeps their exact same server.

Quick
Reference.

Consistent hashing
Maps both servers and keys onto the same hash ring, so only a small fraction of keys move when the cluster resizes.
Hash ring
A circular hash space where a key belongs to the next server found going clockwise from its position.
Virtual nodes
Multiple ring positions per physical server, used to balance load evenly across an uneven cluster.
Remapping fraction
Roughly 1/N of keys move per node change, versus nearly all of them under naive modulo hashing.

Caption
Add a single server to a cluster of four, and the naive approach remaps roughly eighty percent of your keys to a different machine. One server changed. Almost everything moved. The naive approach is hash(key) modulo the number of servers. It is simple and it works fine right up until the server count changes. The moment you add or remove even one machine, the divisor in that modulo operation changes, and nearly every key gets sent to a completely different index than before. For a cache, that means an instant, nearly total wipeout the moment you scale. For a sharded database, it means a massive, unnecessary data migration triggered by a single node change. Consistent hashing fixes this by changing what gets hashed. Instead of hashing keys against a count, you hash both the servers and the keys onto points on the same circular space, a ring. A key belongs to whichever server is the first one found going clockwise from the key's position on that ring. Add a new server, and it only claims the keys sitting between it and the previous server going backward. Remove a server, and only the keys it owned move on to the next server clockwise. Nobody else on the ring is affected at all. That difference in ratios is the entire point. Naive modulo hashing invalidates something close to N out of N keys on every resize. Consistent hashing invalidates roughly one out of N. In real systems, you also add virtual nodes: each physical server gets hashed to many points around the ring rather than just one, which spreads load evenly and prevents any single node from absorbing an oversized chunk of the keyspace when its neighbors change. This is exactly how DynamoDB and Cassandra partition data across nodes, why memcached clients implement consistent hashing on the client side, and how CDNs route requests to edge nodes without cache hit rates collapsing every time the edge fleet scales. One elegant idea removes an entire class of operational pain that shows up every single time infrastructure needs to grow or shrink. #consistenthashing #distributedsystems #systemdesign #databases #softwareengineering #ravenextechnologies
