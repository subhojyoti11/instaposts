02 / 06

Why GET and
POST Both Fail.

GET: too small
Browsers and servers cap URLs around 2,048-8,192 characters, and GET has no request body. Stack in 30 filters and you trip a 414 URI Too Long error, since every filter must be serialized into the URL string itself.
GET: still ideal
GET is safe, idempotent, and cacheable, exactly what a read-only search wants, and its semantics are perfect for reading data. It just can't carry the payload.
POST: wrong tool
POST carries a full request body, so complex filters fit easily as JSON, but POST means create or modify a resource, not fetch one, so using it to read data breaks that contract.
POST: the cost
Repeating a POST can trigger duplicate side effects, and browsers, CDNs, and gateways never cache it by default. Retrying a timed-out request isn't safe, and every "read" still hits the origin server.

One Verb.
Both Wins.

# A GET-style request that carries a POST-style body QUERY /products HTTP/1.1 Host: api.example.com Content-Type: application/json { "filters": { "category": "electronics", "price": { "min": 100, "max": 500 } }, "sort": "price_asc" }

Same safe, idempotent, cacheable contract as GET. Same rich JSON body as POST. RFC 9458 makes it official.

04 / 06

GET vs POST
vs QUERY.

Request body
GET has none. POST and QUERY both carry a full JSON body.
Safe & idempotent
GET and QUERY never alter state and can be retried freely. POST can, and often does.
Cacheable
GET and QUERY responses can be cached by content. POST is not cached by default.
Best for
GET fits simple lookups, POST fits mutations, QUERY fits complex reads. Three verbs, three distinct jobs.

06 / 06

Quick
Reference.

QUERY
New HTTP verb combining GET's safety with POST's body. Safe, idempotent, cacheable, and body-carrying.
414 error
"URI Too Long," triggered when a GET query string exceeds server limits. The original problem QUERY solves.
Idempotent
Repeating the same request produces the same result with no extra side effects. True for GET and QUERY, not guaranteed for POST.
RFC 9458
The IETF standard formally defining the QUERY method. Adoption depends on servers and gateways supporting it.

Caption
HTTP has a new verb, and it fixes a problem developers have been hacking around for years. Say you're building a search endpoint with 30 or 40 optional filters. A GET request is the semantically correct choice: it's safe, idempotent, and every response is cacheable. But GET has no request body, so every filter has to get crammed into the URL. Browsers and servers cap URL length around 2,000 to 8,000 characters, and a complex filter set blows past that limit fast, returning a 414 URI Too Long error. So developers reach for POST instead. POST happily carries a full JSON body, filters and all. But POST was never meant to read data, it means create or modify a resource. It isn't idempotent, so retrying a failed request can trigger duplicate side effects, and browsers, CDNs, and API gateways never cache a POST response by default. Every "read" ends up hitting the origin server again. QUERY, defined in RFC 9458, closes that gap. It carries a rich JSON body like POST, but keeps the safe, idempotent, cacheable contract of GET. The server treats it purely as a read: no state changes, no duplicate writes, and caching works based on the body content rather than the URL. Instead of a search request truncated into an unreadable query string, an API can accept a clean, structured body. A QUERY request to /products with a JSON payload describing category, price range, and sort order is understood by the server as a pure fetch, not a mutation. The catch is adoption. Frameworks, reverse proxies, API gateways, and firewalls all need to recognize QUERY as a legitimate verb and route it correctly. Older middleware built around the classic four methods may reject it outright.
