Overwrites

# The CRUD approach UPDATE accounts SET balance = balance - 50 WHERE id = 42;

The moment this runs, the previous balance is gone. You cannot answer "what was my balance last Tuesday" or "why did this change", because the row only ever remembers right now.

The real cost
No audit trail, no debugging history, no way to replay a bug that only shows up after ten mutations to the same row.

Replaying
the Log.

# Deriving current state from the event log def current_balance(events): balance = 0 for event in events: if event.type == "Deposited": balance += event.amount elif event.type == "Withdrawn": balance -= event.amount return balance # never mutated in place

Want the balance as of last Tuesday? Replay every event up to that timestamp. The full history was never thrown away.

07 / 07

Quick
Reference.

Event sourcing
Stores every state change as an immutable event instead of overwriting a row with the latest value.
Event store
An append-only log of everything that has ever happened, the single source of truth in this architecture.
Projection
The current state, derived by replaying events from the beginning, or from the last saved snapshot.
Snapshot
A cached checkpoint of derived state so you don't replay millions of events just to answer what the balance is right now.

Caption
Your bank balance is not a number sitting quietly in a database cell. It is the result of replaying every deposit and withdrawal you have ever made, from the very first one, every single time you check it. The obvious way to store a balance is a row you update in place. UPDATE accounts SET balance = balance minus fifty WHERE id equals forty two. It is simple, and the instant it runs, the previous balance is gone. There is no way to answer what your balance was last Tuesday, or why it changed at 3pm on a specific date, because the row only ever remembers whatever the most recent write left behind. For anything that needs an audit trail, and a bank always does, that is disqualifying. Event sourcing stores the opposite thing. Instead of the current balance, you store every event that ever changed it: AccountOpened, Deposited fifty, Withdrawn twenty, Deposited thirty, appended to a log that is never edited, only ever added to. The current balance is not stored anywhere. It is derived by starting at zero and replaying every event in order, adding deposits and subtracting withdrawals, until you arrive at the present. Want the balance as of last Tuesday? Replay the same log, but stop at that timestamp. Nothing was thrown away, so nothing needs to be guessed at. This obviously costs more storage than a single mutable row, since every event is kept forever instead of just the latest value. In exchange you get a complete, queryable history and the ability to reconstruct state at any point in time, which is why real banking ledgers work exactly this way, both by regulation and by necessity. It shows up outside finance too. Git is event sourcing: every commit is an immutable event, and your working directory is just the replay of every commit up to HEAD. Systems built on Kafka often use its log directly as the event store, letting multiple independent services build their own view of the world by replaying the same underlying stream. The one practical wrinkle is replay cost at scale, which is why real systems take periodic snapshots, cached checkpoints of the derived state, so you don't replay a million events just to answer what the balance is right now. #eventsourcing #systemdesign #softwarearchitecture #distributedsystems #backenddevelopment #ravenextechnologies
