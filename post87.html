03 / 07

P Isn't
Optional.

The "pick two" framing is misleading. Network partitions are not a choice you opt out of, cables get cut, data centers lose connectivity, packets get dropped. Partition tolerance is a fact of distributed systems, not a design decision.

The real choice only happens during a partition. When nodes can't reach each other, do you sacrifice Consistency or Availability? That is the only decision CAP actually gives you.

The Decision
at Split-Brain.

# A write arrives during a network partition def handle_write(node, key, value): if node.can_reach_quorum(): # CP choice: only commit with agreement return commit(key, value) else: # AP choice: accept anyway, reconcile later return accept_locally(key, value)

CP rejects the write and returns an error. AP accepts it locally and resolves conflicting versions once the partition heals.

Quick
Reference.

CAP theorem
During a network partition, you must choose between Consistency and Availability. You cannot have both.
CP system
Refuses requests it cannot guarantee are correct, prioritizing consistency over uptime.
AP system
Keeps answering requests during a partition, accepting temporary inconsistency to stay available.
PACELC
Extends CAP to cover the normal, non-partitioned case, where you still trade latency against consistency.

Caption
Every distributed database will tell you it gives you Consistency, Availability, and Partition tolerance. The moment the network actually splits, you find out that was never a real promise. The CAP theorem, proven formally by Gilbert and Lynch in 2002, states that a distributed system can only guarantee two of these three properties at once. Consistency means every read returns the most recent write, no matter which node answers. Availability means every request gets a response, even if some nodes are unreachable. Partition tolerance means the system keeps functioning even when the network splits and nodes cannot talk to each other. Here is the part most summaries get wrong. "Pick two" makes it sound like Partition tolerance is optional, something you could design away if you tried hard enough. It is not. Cables get cut, data centers lose connectivity, packets get dropped, this is simply what happens at scale. Any distributed system that spans more than one machine will eventually face a partition whether it wants to or not. So the real choice was never among three options. It only ever comes down to two, and it only ever gets made at the exact moment a partition occurs: when a node cannot reach the rest of the cluster, does it stay silent and correct, or does it answer and risk being wrong? A CP system chooses correctness. If it cannot reach a quorum of other nodes to confirm a write is safe, it refuses the request outright rather than risk serving stale or conflicting data. ZooKeeper and etcd work this way, because coordination state that is wrong is worse than coordination state that is temporarily unavailable. An AP system chooses uptime. It accepts the write locally, keeps serving requests, and reconciles any conflicting versions once the partition heals. Cassandra and DynamoDB default to this, because a shopping cart or a social feed being briefly stale is a far smaller problem than the whole system going dark. The theorem also has a well-known sequel. PACELC points out that even with no partition at all, you are still trading Latency against Consistency on every single request, which is the tradeoff CAP never mentions because it only describes the partition case. Knowing which one your database defaults to, and why, tells you more about its real behavior than almost anything else in its documentation. #capdotheorem #distributedsystems #databases #systemdesign #softwareengineering #ravenextechnologies
