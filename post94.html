Why RAG
Can Fail.

The workflow
Hundreds of PDFs get broken into text chunks, embedded as vectors, and stored in a vector database. Your question is embedded the same way and matched by proximity.
Missed information
Semantic search works on probability, not certainty, so crucial chunks can be completely missed and never reach the model at all.
Random results
That probabilistic matching means answers can come back inaccurate or inconsistent even when the right document was sitting in the database the whole time.
High latency
Retrieving and reassembling context from hundreds of scattered chunks adds real, measurable delay before the model can even start generating.

06 / 06

Quick
Reference.

Open Knowledge Format
One AI-generated Markdown file per source document, explicitly linked to related files instead of embedded as vectors.
LLM Wiki
The originating concept, introduced by Andrej Karpathy, of structuring an AI's knowledge as a readable, linked wiki rather than a vector index.
Semantic search
Traditional RAG's retrieval method: nearest-neighbor matching in vector space. Probabilistic, and prone to missing relevant chunks.
Deterministic retrieval
Following explicit, pre-built links between files instead of guessing relevance from vector distance.

Caption
Traditional RAG has a quiet reliability problem, and most teams have just learned to live with it. The standard workflow is familiar by now. Hundreds of company PDFs get broken into text chunks, each chunk gets converted into a vector embedding, and everything lands in a vector database. When you ask a question, your prompt gets embedded too, and a semantic search finds the nearest vectors to hand off to the model. It works, most of the time, which is exactly the problem. Semantic search operates on probability, not certainty, so crucial chunks can be missed entirely even when they were sitting right there in the database. That same probabilistic matching produces results that are sometimes inaccurate or wildly inconsistent between similar queries. And because the system has to retrieve and reassemble context from potentially hundreds of scattered chunks, the whole process adds real latency before generation even starts. An alternative structure, inspired by Andrej Karpathy's "LLM Wiki" concept, skips vector embeddings entirely. An AI reads every source document and writes one structured Markdown file per document, containing a clear description of its contents. Instead of relying on mathematical proximity to decide what is related to what, the AI explicitly maps and records the links between files itself, the same way a well-maintained wiki links related pages to each other. The retrieval difference is the whole point. A question about revenue searches only revenue.md and whatever it explicitly links to, not the entire corpus. If revenue.md needs data that actually lives in payments.md, the system follows that pre-established link directly instead of hoping a nearest-neighbor search happens to surface the right chunk. Retrieval becomes deterministic instead of probabilistic, and it only has to search a small, targeted set of files instead of scanning a scattered vector index. The tradeoff is upfront cost. Building the knowledge graph means processing every document once to generate summaries and links, before a single query is ever asked. In exchange, every query afterward is faster, more accurate, and easier to explain than "the embedding was close enough." #rag #knowledgegraph #llm #airesearch #systemdesign #ravenextechnologies
