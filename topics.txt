201. AI Looping vs Prompting
- Focus: Why single-shot prompting is dead. How agentic loops work: the model receives a Goal, generates a response, critiques its own output, writes its next prompt, and iterates until the goal is met — acting as its own QA manager.
- Key angle: Prompting = command → answer (you do the heavy lifting). Looping = Goal → self-critique → self-prompt → repeat (the model does the heavy lifting). Real-world shift already happening in Cursor, Devin, and OpenAI's o3 reasoning loops.

202. The HTTP QUERY Method (RFC 9458)
- Focus: Why HTTP needed a fifth verb. GET can't carry a body and hits URL length limits (414 errors) on complex, multi-filter search requests; POST carries a body but is non-idempotent and non-cacheable, corrupting caches and monitoring when misused for reads.
- Key angle: QUERY merges both: a body-carrying request that stays safe, idempotent, and cacheable, like GET, but shaped like POST. Lets APIs send structured JSON filter objects instead of unreadable, truncatable query strings. Adoption is gated on servers, gateways, and firewalls learning to route the new verb.

203. Open Knowledge Format: RAG Without Vectors
- Focus: Traditional RAG breaks documents into chunks, embeds them as vectors, and retrieves via semantic search at query time. That search is probabilistic, not exact, so relevant chunks get missed, results come back random or inaccurate, and scattering context across hundreds of chunks adds real latency.
- Key angle: Inspired by Andrej Karpathy's "LLM Wiki" concept, the alternative skips embeddings entirely. An AI generates one structured Markdown file per source document plus explicit links between related files (revenue.md links to payments.md), building an open knowledge graph instead of a vector index. Queries are then resolved deterministically by following those pre-built links to the exact files that matter, trading nearest-neighbor guessing for faster, more accurate, explainable retrieval.

204. IRCTC's Tatkal Crash: The Strict Consistency Problem
- Focus: Why a faster frontend on IRCTC's new website (rebuilt on the beta released mid-2026, with captchas and pop-ups stripped out) still won't stop Tatkal from crashing. Booking a train seat isn't like an Instagram like count where two users seeing different counts is harmless — if two people are both shown seat 42 in coach S4 as available, that's a correctness failure, not a UX glitch. This requirement, strict consistency, means every booking must resolve through one locked, single source of truth instead of the horizontally-replicated, eventually-consistent architecture services like Google or Instagram can get away with.
- Key angle: Tatkal is a worse-case flash sale — not thousands of items sold to a spread-out crowd, but a few hundred seats on one train hit by the entire country in the same second, a thundering-herd spike severe enough to have crashed billion-dollar ticketing systems like Ticketmaster during high-demand on-sales. Trimming frontend steps only reduces request volume; the real bottleneck is the decades-old Passenger Reservation Engine handling the actual seat-locking transaction underneath, so whether the new system holds up is only provable under real peak load, not a calm launch day.

205. GitHub Stacked PRs
- Focus: Why dependent pull requests used to be so painful to manage. When one PR builds on code from another still-unmerged PR, the second author has to keep pulling in the first branch's commits, and every time the first PR changes, that dependency forces a rebase that can spiral into repeated merge conflicts, with the second PR's diff cluttered by changes that aren't even theirs.
- Key angle: GitHub's Stacked PRs let a contributor open a new PR directly on top of another still-open PR instead of on the trunk branch, and GitHub tracks the dependency chain automatically, PR two depends on PR one, PR three can depend on PR two, and so on. Each PR's diff shows only its own actual changes, conflicts drop sharply since rebasing happens against a known, explicit parent instead of a moving target, and the review stays scoped to just the relevant work, letting a large feature ship as an ordered sequence of small, reviewable PRs instead of one tangled branch.

206. GEO (Generative Engine Optimization)
- Focus: Why classic SEO is losing ground as Google increasingly answers queries directly inside an AI-generated summary box instead of a page of blue links. When the answer is synthesized on the results page itself, fewer searchers ever click through to the source site, so ranking well in traditional search no longer guarantees traffic the way it used to.
- Key angle: GEO shifts the goal from ranking for a keyword to getting a site's content actually cited or drawn on inside an AI answer. That favors specific, hard-to-generate signals over generic content: original case studies and firsthand data an AI can't fabricate, content structured around the literal questions people type into a search or chat box, and dedicated FAQ-style pages that answer those questions directly and completely, since those formats are exactly what a generative answer engine tends to pull from and attribute.

207. Portable Offline AI on a USB Drive
- Focus: Running a full local chatbot entirely off a plain flash drive, no internet connection, no cloud account, and no data ever leaving the machine it's plugged into. The two pieces that make this possible are a lightweight, self-contained inference server binary and a quantized model file small enough to fit alongside it.
- Key angle: A quantized GGUF model compresses a model's weights down to a few gigabytes with reduced but usable precision, small enough to carry on ordinary consumer storage, while a portable llama.cpp-style server binary needs no installation, it just runs directly from the drive and exposes a local web address on whatever machine it's plugged into. Point a browser at that local address and the entire chat interface, model, and inference all run offline on that one laptop, making the flash drive itself the whole deployable AI, useful anywhere internet access or data privacy is a constraint.

208. LLM Watermarking (Green/Red Token Lists)
- Focus: Why marking AI-generated text as metadata never worked, metadata is just a removable tag describing a file, stripped in seconds, so it can't reliably prove text came from a model. Detecting AI text needs a signal baked into the words themselves, not an attachable label.
- Key angle: At each generation step, a language model is choosing its next word from a probability distribution over many candidates. A watermarking scheme splits that candidate vocabulary into two pseudorandom groups per step, informally a "green" list and a "red" list, and nudges the model's sampling to prefer green-list tokens slightly more often than chance would. Individually invisible, but across a full paragraph the green-token frequency skews measurably above fifty percent in watermarked text, letting the model's own detector flag authorship statistically without touching metadata at all. Regulatory pressure, particularly the EU AI Act's requirement that AI-generated content be identifiable, is what pushed labs to adopt this at all, with some rolling it out globally rather than region by region.
