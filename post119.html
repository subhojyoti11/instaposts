03 / 07

Three Ways to
Count Out Cash.

🔁
BRUTE FORCE
Try everything
Goal
Check every possible mix of notes that sums to the amount.
Focus
Exhaustively tests combinations until one works.
Result
Correct, but far too slow for every withdrawal.
🏃
GREEDY
Biggest note first
Goal
Always use the largest note that still fits.
Focus
Repeatedly subtracts the biggest available denomination.
Result
Fast and usually right, but can fail on odd note sets.
🧮
DYNAMIC PROGRAMMING
Build up the answer
Goal
Compute the minimum notes for every smaller amount first.
Focus
Reuses previously solved smaller amounts to solve the full one.
Result
Always correct, and fast enough for real-time dispensing.

Solving Every
Smaller Amount First.

Denominations are fixed and knownThe machine only ever works with a small, fixed set of note values it currently has loaded.
Smaller amounts solved firstThe algorithm calculates the minimum notes needed for every smaller amount, in order.
Each answer reuses the lastThe best way to make a given amount is built directly from the best way to make a smaller one.
The cassette count constrains itThe final choice also has to respect how many notes of each type are actually left.

05 / 07

The Loop, in
Pseudocode.

# Minimum notes needed for an amount def min_notes(amount, notes): best = [0] + [infinity] * amount for a in range(1, amount + 1): for n in notes: if n <= a: best[a] = min(best[a], best[a - n] + 1) return best[amount]

The machine never gambles on a combination. It already knows the cheapest way to make every smaller amount before it ever answers yours.

Quick
Reference.

Coin change problem
A classic algorithmic problem: finding the minimum number of denominations that sum to a target.
Greedy algorithm
An approach that always makes the locally best choice, fast but not always globally correct.
Dynamic programming
Solving a problem by building up answers to smaller subproblems and reusing them.
Denomination set
The specific fixed values of notes or coins a system has available to use.

Caption
An ATM never guesses which bills to hand you. Before it dispenses a single note, it has already computed the mathematically fewest notes possible to make your exact amount. The naive approach would be trying every possible combination of available notes until one happens to add up correctly, which technically works but is far too slow to run every time someone withdraws cash, especially with several denominations to consider. A faster shortcut is a greedy approach, always grabbing the largest note that still fits under the remaining amount and repeating. That's fast and usually correct with common denomination sets, but greedy reasoning can quietly fail on certain combinations of note values, leaving you with more bills than necessary or, worse, no valid combination at all. What machines actually run is dynamic programming, the same technique behind the classic coin change problem. Instead of searching blindly, the algorithm first calculates the minimum number of notes needed to make every amount smaller than your request, one at a time, in order. Each of those smaller answers gets reused to build the next one, since the cheapest way to make a given amount is always just one note added to the cheapest way to make some smaller amount. By the time the calculation reaches your actual requested amount, the answer is already guaranteed to be the true minimum, not a guess and not a greedy shortcut that might be wrong. Real machines layer more onto this too, factoring in exactly how many notes of each denomination remain loaded in each cassette, so the dispenser doesn't drain one denomination empty while ignoring another. The identical minimum-coin logic runs inside vending machines and point-of-sale terminals calculating your change, anywhere a fixed set of denominations needs to sum to an exact amount instantly and correctly.
